# Supabase setup and integration
Project name, Paris region, free plan and healthy status were reported in the supplied brief; not verified live. No project URL/ref or credentials are supplied. Enter secrets only in local tooling or provider settings, never chat/git.

1. Sign into the intended Layverse Supabase project. Verify project ref/name and inspect existing public tables and migration history. These migrations assume a fresh schema with no colliding names. If tables already exist, reconcile via a new migration; do not reset remote data.
2. Install/currently supported Supabase CLI and local Docker if using the local stack. At repository root run `supabase init` once (do not overwrite an existing config), then `supabase start`. Set local `[auth] enable_anonymous_sign_ins = true` in generated config; restart as needed. `supabase db reset` is ONLY for disposable local data. It applies migrations and configured seed. Run the database suite as documented in TEST_PLAN.
3. In hosted Auth settings enable Anonymous Sign-Ins. Configure the recommended CAPTCHA/Turnstile abuse protection for a public deployment, wire its token into signInAnonymously and verify allowed domains/rate limits. If configuration is blocked, resolve it before public guest writes; never replace authentication with public write policies.
4. Authenticate CLI locally (`supabase login`), link verified project (`supabase link --project-ref <actual-ref>`), inspect changes with `supabase db push --dry-run`, then `supabase db push`. Current CLI flags must be checked with `--help`. Do not run remote reset. Apply `supabase/seed.sql` once through authenticated SQL Editor after migrations; seed is safe to rerun and contains no private plans.
5. Copy public project URL and publishable key to local `.env.local`, using `.env.example`. Legacy anon key may be used if that is what the project exposes; neither grants privileged ownership. Never use service-role/secret keys in VITE_ variables. Use same variable names in Vercel Preview/Production with the intended environment's project.
6. Generate `src/types/database.types.ts` from the actual schema: `supabase gen types typescript --linked > src/types/database.types.ts`. Instantiate one typed supabase-js client with session persistence and auto-refresh. No auth call during module import; use a serialized ensureGuestSession function before first save. Browsing catalogue needs no sign-in.
7. Initialize RPC inputs exactly as ARCHITECTURE.md. Do not calculate owner in client or send arbitrary table writes. Re-fetch after save; show database-confirmed revision and timestamp. Read items ordered by position.
8. Test live project with two independent browsers/sessions: A saves; B cannot list/read/edit A's UUID; logged-out request cannot save; both can browse catalogue. Test actual PostgREST and Auth, not SQL Editor superuser queries alone.
9. Check database advisor/security warnings, migration history, seed counts and project health. Capture nonsecret evidence in VALIDATION.md. Keep backup/demo plan and stable catalogue. Never export auth tokens into screenshots.

Guest recovery: browser session persists across refresh, not across cleared storage or a new device. No sign-out button needed for demo; disclose limitation. If session expires refresh it before retry. If session is gone, do not promise access to old plans from a new anonymous identity.
